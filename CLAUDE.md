# CLAUDE.md

EPICC (Epigenetic Pipeline for Integrative Chromatin Characterization) — Snakemake pipeline for ChIP-seq, RNA-seq, small RNA-seq, bisulfite methylC-seq, and direct methylation from long-read sequencing.

## Running the Pipeline

```bash
conda create -n epicc -y --file config/epicc-env.txt && conda activate epicc
epicc run --samples your_samples.tsv --cores 12              # local
epicc run --samples your_samples.tsv --profile profiles/slurm # SLURM cluster
epicc validate --samples your_samples.tsv                     # config check + dry-run
epicc validate --build-envs --samples your_samples.tsv        # pre-create rule conda envs
                                                              # (run from a login/dev node
                                                              # before sbatch-wrapped runs
                                                              # on clusters where conda
                                                              # env create fails inside a
                                                              # SLURM allocation)
```

`epicc` is a thin argparse wrapper around snakemake; subcommands are `run`, `validate`, `output`, `unlock`, `perf`, `clean`, `init-profile`. Anything after `--` is forwarded verbatim to snakemake. Raw `snakemake ...` invocations still work but bypass `epicc`'s placeholder-detection and TMPDIR routing.

`epicc init-profile TYPE [NAME]` copies a bundled cluster profile template (`slurm` or `uge`) to `~/.config/snakemake/NAME/config.yaml` — the XDG path Snakemake searches when `--profile NAME` is used. Recommended setup for conda-install users and the standard path when sharing a profile across multiple projects. Use `--force` to overwrite an existing profile.

`run` and `validate` accept named overrides for commonly-tuned settings (all override the options YAML):
- `--chip-aligner {bowtie2,chromap}`, `--atac-aligner`, `--chip/atac-mapping-strategy`
- `--[no-]full-analysis`, `--[no-]te-analysis`, `--[no-]go`, `--[no-]rna-deduplicate`, `--methylation-contexts CG,CHG,CHH`
- `--dmr-caller {metilene,dmrcaller}`, `--dmr-min-diff SPEC` (`auto` / float / `CG=f,CHG=f`), `--dmr-min-cytosines`, `--dmr-q-value`, `--dmr-sigma-n`
- `--chip-callpeaks-params STR`, `--cut-broad-caller {epic2,seacr,macs2}`, `--cut-narrow-caller {seacr,macs2}`
- `--analysis-name NAME` (sets `analysis_name`; shared with `output` via `add_common_options`, checked by `_analysis_name` against the sample sheet's unsafe-char set plus no `__` / leading or trailing `_`, since it is a `__`-delimited field of output paths)
- `--ref-genome GENOME` (sets `only_genome`: rows for other genomes are dropped before validation, so those genomes need no config entry), `--te-file PATH` (writes `genomes.<GENOME>.alt_te_file`; the genome is `--ref-genome` or the sheet's only one)

`epicc output --plot-type browser` also takes `--te-file` and `--extra-tracks BED,…` with optional `--extra-tracks-labels` / `--extra-tracks-colors`, which replace `browser_extra_tracks` for that run (normalized by `workflow/scripts/browser_extra_tracks.py`).

`run --auto-unlock` clears a stale `.snakemake/locks/` before starting. `validate` accepts the flag so a run's command line can be reused, but never unlocks — it is run beside active runs, and a lock file can't tell a live run from a killed one. A dry-run only warns about a lock, so `validate` passes regardless and then prints a note that `epicc run` will be refused.

Nested settings (`dmr_thresholds.*`, `chip_callpeaks.params`, `cut_callpeaks.*`) are applied via a temp merged config file, written under the run directory's `.snakemake/epicc/` rather than `/tmp` because cluster jobs re-read `--configfile` on their own node; sibling keys not specified on the CLI are preserved from the options YAML.

## Architecture

### Snakemake Structure

- `workflow/Snakefile` - Main orchestrator; loads config, parses sample metadata, includes rule modules
- `workflow/rules/` - Modular rule files by data type:
  - `environment_setup.smk` - Reference genome preparation (indexing, annotation processing)
  - `sample_download.smk` - SRA download and FASTQ processing
  - `ChIPseq.smk` - Histone/TF ChIP mapping, peak calling (MACS2), IDR analysis
  - `ATACseq.smk` - ATAC-seq mapping and peak calling (shares ChIP conda env)
  - `RNAseq.smk` - STAR alignment, differential expression (edgeR)
  - `mC.smk` - Bismark alignment, methylation calling, DMR analysis (DMRcaller)
  - `smallRNA.smk` - ShortStack analysis, structural RNA filtering
  - `combined_analysis.smk` - Cross-datatype heatmaps, metaplots, browsers (deeptools)
- `workflow/scripts/` - R and Python scripts for statistical analysis, plotting, and sample-sheet utilities
- `workflow/envs/` - Conda environment YAML files per analysis type

### Sample Sheet and Naming

Sample metadata is defined in a TSV file with 10 columns:

`Assay | Genome | Levels | Replicate_ID | Read_files | Read_layout | IP_target | Control | Peak_type | Comments`

- **Sample_ID** is not a column (#91): `derive_sample_id` builds it as `{level values}_{tag}_{Replicate_ID}`, tag = `ChIP_`/`CR_`/`CT_` + `IP_target` for ChIP/CUT_RUN/CUT_TAG (control rows too: `WT_ChIP_Input_rep1`), or the `ASSAY_SHORT` token (`RNA`, `sRNA`, `WGBS_nd`, …). Genome, Peak_type, Read_files, Read_layout, Control and Comments never contribute. `read_sample_sheet` derives it before the genome explode, so `Sample_ID` stays an ordinary internal column and nothing downstream changed. Two rows deriving the same ID for one genome is an error; each part is checked against the unsafe-char set and for `__`/leading/trailing `_`, reported against its source column. A sheet that still has a `Sample_ID` column is rejected — no compatibility layer; the repo's sheets were converted instead. The builder mirrors the rule in `deriveSampleId` (parity tested over every shipped sheet in `tests/unit/test_builder_sample_id.py`), shows the ID read-only, never exports it, and rewrites Controls when a referenced row's ID changes (`adoptDerivedIds`).
- **Assay**: Controlled vocabulary (experimental method only): `ChIP`, `CUT_RUN`, `CUT_TAG`, `ATAC`, `RNAseq`, `RAMPAGE`, `sRNA`, `WGBS`, `WGBS_nd`, `PBAT`, `EMseq`, `dmC`.
- **Genome**: Reference genome name (e.g. `Spombe`, `ColCEN`), or a comma-separated list (`B73,W22`) to map the same reads to several references. Multi-genome rows are exploded internally into one row per `(Sample_ID, Genome)`. A genome name must not contain `__`.
- **Levels**: Comma-separated `factor:level` pairs (e.g. `genotype:WT,tissue:root`). All samples must have the same factors. No `=` in factor names or levels (reserved by the UpSet `label=type` map).
- **Replicate_ID**: Replicate identifier (e.g. `rep1`, `rep2`)
- **Read_files**: SRA accession (`SRR12345`), local path, HTTP(S) URL, public S3 URI (`s3://bucket/key`), or `+`-separated for merging multiple inputs (`+`-merge supported for SRA accessions and FASTQ files, local or URL; BAM/bedMethyl must be merged upstream)
- **Read_layout**: `SE` or `PE`
- **IP_target**: Required for pulldown assays (`ChIP`/`CUT_RUN`/`CUT_TAG`; e.g. `H3K9me2`, `WCE`, `Input`). Blank for others.
- **Control**: derived Sample_ID of the control sample (e.g. WCE or Input for ChIP). Chain depth is capped at 2: a control may declare its own Control — the *dual-role* case, where a sample is both another row's control and an analysis target itself (e.g. H3 as H3K9me2's control while normalized against Input) — but that one must not. A pulldown row with no Control is not peak-callable and is dropped from peak/analysis targets (`is_peak_call_target`).
- **Peak_type**: `broad` or `narrow` — the peak-calling type, separate from Assay. Required on `ChIP`/`CUT_RUN`/`CUT_TAG` rows that call peaks, i.e. those with a `Control` (broad for histone domains, narrow for TFs/sharp marks). Optional on a control-only row, which calls no peaks and whose peak type reaches no output path; must be blank for every other assay.
- **Comments**: Optional free text for the user's own notes. Unconstrained, not assay-gated, and completely inert — never read by the pipeline and never part of analysis keys, names, or output paths. The column may be absent entirely (filled with `""`). Tabs/newlines are stripped on builder export so the TSV stays intact.

Control-row replicate merging keys on `(Levels, IP_target, Genome)` only — the `Assay` value on a control row is decorative for merging purposes, so a single biological Input/IgG/WCE serving multiple IP types (broad + narrow, ChIP + CUT&RUN) merges correctly regardless of how individual rep rows are labeled. See `build_control_merge_key` in `workflow/scripts/sample_sheet.py`.

Per-replicate naming splits at the alignment boundary. Everything up to and including read trimming is genome-independent and uses the bare `Sample_ID` (e.g. `trim__WT_ChIP_H3K9me2_rep1__R1.fastq.gz`), so one download+trim serves every reference the sample is mapped to. From alignment onward the reference is part of what the file *is*, so paths use `mapped_name` = `{Sample_ID}__{Genome}` (e.g. `final__WT_ChIP_H3K9me2_rep1__ColCEN.bam`). `parse_sample_name` accepts either form; `base_sample()` strips the genome for pre-alignment inputs of boundary rules. This is what lets one sample be mapped to several genomes without output collisions (issue #39). Analysis-level (merged replicate) files use a derived name: `{Assay}__{levels_label}__{IP_target}__{Genome}` (e.g. `ChIP_broad__WT__H3K9me2__Spombe`).

Peak type is set in the **Peak_type** column: `broad` (histone-domain marks: H3K9me2, H3K27me3, …) or `narrow` (TFs, H3K4me3, H3K27ac, …). The three pulldown assays (`ChIP`/`CUT_RUN`/`CUT_TAG`) share the `ChIP` env (`results/ChIP/`). Internally, `sample_sheet.py` folds `Assay`+`Peak_type` into a combined token (`ChIP_broad`, …) used for env/peaktype lookups and output naming (`add_compat_columns` / `combine_assay_peaktype`); validation runs on the separated form, before the fold. Default peak callers: ChIP → MACS2; CUT&* broad → epic2; CUT&* narrow → SEACR. Override via `cut_callpeaks.{broad,narrow}_caller` (`epic2`, `seacr`, `macs2`).

Central sample-sheet logic lives in `workflow/scripts/sample_sheet.py`.

### Tools

- `tools/epicc-builder.html` - Self-contained HTML5 app for building sample sheets and options files. Tabulator-based editor with validation, dynamic factor columns, per-cell examples, and YAML options export. Open directly in a browser. `#`-prefixed sample lines import as greyed-out *commented* rows (`_commented`, toggled by "Comment Selected"); they are skipped by validation except as a Control target (error) or an ID clashing with an active row (warning), and export with their original `#` prefix. Other `#` lines and blank lines are kept (`sheetPreamble`, per-row `_notesBefore`, `sheetTrailer`) so import→export is byte-identical. Tests: `tests/unit/test_builder_commented_rows.py`.
- `dev/profile_snakemake_log.py` - Snakemake log profiler. Parses `.snakemake/log/*.snakemake.log` files and reports per-rule timing, phase summary, slowest jobs, and parallelism stats. Supports markdown (stdout) and self-contained HTML with Gantt timeline chart. Default mode auto-aggregates all logs from the same resumed run, identified by `output_dir` + `analysis_name` wildcards extracted from log content (not timestamps). The positional argument accepts either a single `.snakemake.log` file or a run's results directory (`output_dir`) — passing a directory aggregates every log matching that `output_dir` signature.
  ```bash
  python dev/profile_snakemake_log.py                       # aggregate latest run
  python dev/profile_snakemake_log.py --html r.html         # HTML report
  python dev/profile_snakemake_log.py --single              # newest log only
  python dev/profile_snakemake_log.py path/to/log.snakemake.log
  python dev/profile_snakemake_log.py results/              # aggregate a run by its output_dir
  ```
- `scripts/subset_test_data.sh` - SLURM-based test data preparation. Downloads SRA data, aligns to a full reference, and subsets reads mapping to a target region (e.g. chr21) for use as integration test fixtures. Self-resubmitting controller with three phases (index, per-sample, gather).

### Configuration

- `config/epicc-options.yaml` - Main options file (paths, parameters, resource allocation)
  - `repo_folder` is optional; auto-detected from `workflow.basedir` at runtime (one level above the Snakefile). Override explicitly only when the repo is accessed from a non-standard path.
  - Reference genomes are namespaced under `genomes:`, each entry containing annotation file paths and species-level parameters (e.g. `genus`, `species`, `ncbi_taxid`)
  - `gtf_file`, `genomesize`, `star_index`, `ncbi_taxid`, and `structural_rna_fafile` are auto-computed at runtime (GTF derived from GFF via gffread, genome stats from FASTA, TaxId from NCBI Datasets CLI, structural RNA FASTA via Infernal/Rfam); user-provided values in the options file override the computed values
  - `structural_rna_classes` controls sRNA structural RNA depletion and replaced the `structural_rna_depletion` toggle. `filter` lists the Rfam classes to deplete (default `[rRNA, tRNA, snRNA]`: rRNA, tRNA and all snRNAs including snoRNAs), and `keep` lists classes exempt from it (default `[]`). A family is depleted when one of its type terms is in `filter` and none is in `keep`, so keep wins; a class in both lists gets a startup warning. `filter: []` turns depletion off: no Rfam scan, no depletion step, even for a genome with an explicit `structural_rna_fafile` (gated by `STRUCTURAL_RNA_DEPLETION` / `depletion_enabled`). The old `structural_rna_depletion: false` still means `filter: []` and `true` is ignored, both with a deprecation warning. A family's class is any term of the `type` column of Rfam's `family.txt.gz` (`Gene; snRNA; snoRNA; CD-box;`), which `Rfam.cm` does not carry; Rfam nests snoRNA under snRNA. `build_structural_rna_db` (cmscan, slow) still annotates all families, and its shell must stay byte-identical. The cheap `select_structural_rna_classes` rule turns `infernal.tblout` into `structural_rnas_selected.fa` with the effective selection (`selection_label`, a filter class that keep cancels dropped) on its params, so a class change reruns only that rule, the bt2 index and the sRNA steps downstream. An explicit `structural_rna_fafile` is used as given (no class selection). The option is active in the shipped options file: Snakemake deep-merges a user configfile over it, so a user `keep` combines with the shipped `filter`, and a user list replaces the shipped one. Logic and validation: `workflow/scripts/rfam_classes.py`.
  - GO database name is auto-derived as `org.<G><species>.eg.db` (e.g. `org.Athaliana.eg.db`) — matches AnnotationForge's strict `org.<G><species>.eg.db` package-name format. To keep multiple reference genomes of the same species (e.g. ColCEN + TAIR10) from colliding in the conda env's shared R library, each genome's GO package is installed into and loaded from `genomes/<refgenome>/GO/` via per-call `lib=` / prepended `.libPaths()`.
  - Access pattern in rule files: `config["genomes"][ref_genome][field]`. The `genomes:` namespace is required; a missing one is a startup error.
  - `methylation_contexts` (default `["CG", "CHG", "CHH"]`) gates per-context mC analysis: bigwigs, DMR calls, and PCA plots are produced only for listed contexts. Set to `["CG"]` for animal genomes where non-CpG methylation is negligible. Subcontexts (CAG/CAA/...) not currently supported.
  - `dmc_methylation.contexts` declares which contexts dmC data carries (unset = `methylation_contexts`). Most ONT models (Dorado `5mCG_5hmCG`) call CpG only, and a CHG/CHH pair with a CpG-only dmC side has nothing to test: `R_call_DMRs_pair_metilene.R` stops on it (metilene segfaults on an empty group), on every attempt. With `[CG]`, a pair with a dmC side is scheduled only in the contexts both sides have (`dmr_contexts_for` in `mC.smk`, logic in `workflow/scripts/mc_contexts.py`), and its `summary__…__DMRs.txt` has no column for the rest; bisulfite pairs keep every run context. It has to be declared: neither a bedMethyl (no context column; `bedmethyl_to_cx_report.py` derives it from the reference) nor a modBAM's MM tags say which contexts were called, so nothing can be read before the DAG is built. Only DMR scheduling uses it; dmC bigwigs and PCA still cover every run context.
  - `dmr_thresholds:` block configures DMR calling parameters for both callers. Shared: `min_diff` (per-context, default CG=0.3/CHG=0.2/CHH=0.1), `min_cytosines` (default 5), `q_value` (FDR significance cutoff, default 0.01 — DMRcaller filters internally on its BH-adjusted pValue; metilene's driver filters its q-value column to match), `min_size` (min DMR length in bp, default 50 — DMRcaller `minSize`; metilene driver applies it post-hoc as `(end-start) >= min_size`, the `metilene_output.pl -l` equivalent). DMRcaller-only: `bin_size`, `min_gap`, `min_reads` (no metilene equivalent — metilene has no between-DMR merge step and consumes per-position rates, not coverage). Metilene-only: `maxdist` (metilene `-M`, max distance in nt between adjacent CpGs in a segment), `valley` (per-context), `maxseg` (per-context). Defaults are Arabidopsis-leaf-tuned; adjust for other organisms/tissues.
  - `chip_aligner` / `atac_aligner` (default `"bowtie2"`) — set to `"chromap"` for ~10x faster mapping. chromap is appropriate for SE-only datasets; PE data shows only 11–28% properly-paired reads with chromap vs 99%+ with bowtie2 (chromap maps ends independently, so one mate is MAPQ-filtered when repeat paralogs are present). When `chip_mapping_strategy` / `atac_mapping_strategy` is `repeat` or `repeatall`, bowtie2 is used automatically regardless of the aligner setting.
  - `use_node_tmpdir` (default `false`) toggles TMPDIR routing — see Key Details below.
- `config/example_samples.tsv` - Documented sample-sheet template (copy and edit; pass to epicc via `--samples`)
- `profiles/slurm/config.yaml` - SLURM executor settings

## Key Details

- Snakemake 9.0+. Results go to `{output_dir}/{env}/` (`ChIP`, `ATAC`, `RNA`, `sRNA`, `mC`, `combined`); genomes to `{genome_dir}/{ref_genome}/`. Both directories default to `results` and `genomes` respectively, configurable via `output_dir`/`genome_dir` config keys or `epicc --output-dir`/`--genome-dir` CLI flags.
- In Python context (input/output/params), paths use `RESULTS_DIR`/`GENOMES_DIR` variables. In shell blocks, paths use `{config[output_dir]}`/`{config[genome_dir]}` Snakemake substitution.
- Env mapping: `ChIP`/`CUT_RUN`/`CUT_TAG` (and the internal combined `_broad`/`_narrow` tokens) → `ChIP`, `ATAC` → `ATAC`, `RNAseq`/`RAMPAGE` → `RNA`, `sRNA` → `sRNA`, `WGBS`/`WGBS_nd`/`PBAT`/`EMseq`/`dmC` → `mC`
- Checkpoint files in `{output_dir}/*/chkpts/` control re-running analyses; delete to force rerun.
- Read_files supports HTTP(S) URLs and public `s3://bucket/key` URIs for FASTQ, BAM, and bedMethyl inputs. S3 support is **public (authentication-free) objects only** — no signing, credentials, or aws CLI. An `s3://` URI is translated to its public HTTPS endpoint in `get_seq_id_and_path` (`s3_uri_to_https`), the single boundary where download paths are produced, so the download rules stay S3-unaware and curl them like any other URL. The region-less global endpoint is emitted (S3 resolves/redirects it; every curl passes `--location`); path-style addressing is used for dotted bucket names, whose labels the `*.s3.amazonaws.com` wildcard cert does not match. Genome config fields (`fasta_file`, `gff_file`, `te_file`, `gaf_file`, `gene_info_file`) also accept URLs — downloaded automatically via curl at rule execution time.
- `te_file` accepts `.bed(.gz)` (pass-through) or `.gff3(.gz)` (auto-converted to BED6 using the GFF3 `ID=` attribute as the name column).
- An `alt_te_file` (set by `--te-file`) replaces `te_file` for the run but never shares its files: it is prepared as `<G>__TE_file_<tag>.bed` by `check_alt_te_file` and analysed as target `all_TEs_<tag>`, the tag from its file name (`workflow/scripts/te_files.py`, which also falls back to a path hash when a different file already holds the tag). Every TE output names its target, so switching annotations between runs reruns nothing and overwrites nothing. Code that consumes the TE file goes through `te_bed_for` / `te_target_for` / `te_suffix_from_target`, never a literal `__TE_file.bed` or `all_TEs`. `check_te_file` and `check_alt_te_file` share `TE_PREP_SHELL`, whose text must stay byte-identical for `check_te_file` — any edit trips Snakemake's code rerun-trigger and re-prepares every genome's TE file, cascading into all TE analyses.
- `epicc clean --tmp` reclaims scratch dirs leaked under `{output_dir}/.tmp/` when a job is SIGKILLed (SLURM timeout, OOM, node failure) and the EXIT trap never runs. Two safety gates, both required: no active SLURM job owns the dir, and it is older than `--tmp-min-age` (default 6 h). An unavailable `squeue` means SLURM-named dirs are skipped, never assumed dead.
- The `shell.prefix` that does TMPDIR routing must itself re-assert `set -euo pipefail`. Snakemake applies strict bash mode only while no prefix is registered (`snakemake.shell._get_process_prefix` gates it on `_process_prefix is None`), so registering one silently turns it off for every rule. Rule bodies here are wrapped in `{ ... } 2>&1 | tee -a "$log"`, which means without `pipefail` a failure anywhere but the last command lets the rule exit 0 — `cat missing_file | pigz > out` produced an empty FASTQ that ran all the way to zero-coverage methylation calls. Any future addition to `shell.prefix` has to keep the `set -euo pipefail` at its head.
- Every bigwig the pipeline builds from a bedGraph goes through `workflow/scripts/bedgraph_to_bigwig.sh`, which pads chromosomes absent from the data with a zero-value base before calling `bedGraphToBigWig`. `bedGraphToBigWig` writes only the chromosomes it sees, and deeptools 4 aborts `computeMatrix` on a query against a chromosome missing from the bigwig header ("The passed chromosome (Chr2) was incorrect"). `bamCoverage`/`bamCompare` tracks (ChIP, ATAC) take the chromosome list from the BAM header and need no padding. The script also orders the input, and avoids `sort` when it can: a bedGraph already grouped by chromosome with ascending starts (true of every one built from a CX report) is split into per-chromosome blocks and concatenated in C order, which is linear. On a 1 Gb genome the CHH track is ~10 GB, and a single-threaded `sort` of it alone ran for hours.
- `merging_mc_replicates` goes through `workflow/scripts/merge_cx_reports.sh`. Bismark's genome-wide cytosine report lists every cytosine, covered or not, so replicate reports hold the same rows for each chromosome — but not in the same chromosome order, which Bismark 3.x varies from run to run. Each report is split into per-chromosome blocks (`workflow/scripts/split_by_chrom.awk`, shared with `bedgraph_to_bigwig.sh`) and the blocks are summed side by side, which is linear but needs TMPDIR space for the uncompressed reports. Reports that don't line up (dmC, which carries only covered positions) fall back to sort + `bedtools merge`, which on a 1 Gb genome did not finish in 8 h.
- `deeptools` is pinned to a major version in the env YAMLs: `deeptools>=4.0.0,<5` in `epibutton.yaml` and `epibutton_rnaseq.yaml`, and `deeptools<5` — capped, not floored — in `epibutton_chip.yaml`, where macs2's newest build is py311 and deeptools 4 requires python >=3.12, so the two cannot coexist. The chip env runs only `alignmentSieve`, `bamCoverage`, `bamCompare` and `plotFingerprint`, none of which changed across the 3→4 boundary; `computeMatrix` and the plotting rules are in `epibutton.yaml`. Freeing that env for deeptools 4 means moving macs2 out of it or on to macs3. It was unpinned until the 3.x→4.x jump, which changed five behaviours the pipeline relied on: bigwig chromosome queries became a hard error (above), `?` in a BED strand column became a panic, `computeMatrix` started naming a single-BED region group after the BED file instead of the fixed label `genes`, `plotProfile`'s default line colormap went from `jet` to the sequential `gnuplot`, and `plotProfile` moved its legend below the axes without growing the figure. The CLI is unchanged — no option EPICC passes was removed and no default differs — so these only show up in the output. That last one silently broke every heatmap and profile — `making_stranded_matrix_on_targetfile` splits a stranded target into plus and minus halves, and under deeptools 3 both halves came back labelled `genes` so `computeMatrixOperations rbind` folded them into one group for free. Under 4 the labels differ, the halves survive as two groups, and every downstream rule (`plotHeatmap`, `plotProfile`, `sort_heatmap`'s `relabel`) passes a single `--regionsLabel` and dies on "length new labels != length original labels". `merging_matrix` now relabels both halves to the target name before the rbind so the merge is explicit rather than a side effect of someone else's default.
- `making_stranded_matrix_on_targetfile` splits a stranded target file into a plus and a minus half and runs `computeMatrix` on each — **not** to orient the regions, which deeptools already does itself from the BED strand column. The split exists so `define_key_for_plots` can pick a *different bigwig* per half: for stranded RNA and sRNA the plus half reads `{sample}__plus.bw` and the minus half `{sample}__minus.bw`, so every gene contributes its sense-strand coverage and the merged matrix holds one sense column per sample. `computeMatrix` takes a single fixed `-S` list, so there is no way to choose the signal file per region strand inside deeptools at any version — the split cannot be collapsed into one call. For `ChIP`/`ATAC`/`mC` both halves read the same bigwigs and the split only costs a doubled `computeMatrix` run; gating it on whether the env has a stranded track would be a legitimate optimisation. A target file whose column 6 is not purely `+`/`-` gets a third `nostrand` pass (`is_stranded` reports `stranded_mixed`): those rows have no sense strand, so they take the plus track and stay their own region group rather than being folded in or dropped. The classification is deliberately not all-or-nothing — 631 of ColCEN's 42,927 TEs are `.` or `?`, and demoting the whole file on their account turned every stranded RNA/sRNA track into separate plus/minus columns.
- `plotHeatmap` runs through `workflow/scripts/plotheatmap_lowmem.py`, never directly. In a PDF, matplotlib draws each rasterized heatmap on an Agg canvas the size of the whole figure (about 4 cm per column at 200 dpi) and hands the backend a cropped *view* of it, and the PDF backend keeps every image until the file is written, so each heatmap kept its full-figure canvas alive: peak memory grew with the square of the column count, about 6 MB × columns² (22.6 GB at 60 columns, 88.8 GB at 120, whatever the region count). The wrapper patches `RendererPdf.draw_image` to take a copy, which lets each canvas go; the PDF's image streams are byte-identical (0.8 GB and 1.4 GB for those two). What remains is deeptools' own copies of the matrix, about 31 bytes per value. Both heatmap rules size `mem_mb` from the matrix header with `heatmap_mem_mb` (`workflow/scripts/heatmap_memory.py`: that model, 1.5× margin, 4 GB floor, times the attempt). Snakemake re-evaluates it just before scheduling, when the matrix exists; until then it falls back to 32 GB. `profiles/default/config.yaml` sets only their runtime, because a `set-resources` `mem_mb` would override the rule's.
- Metaplot y-limits are padded by a tenth of the data's **range**, not of its value. Multiplying the endpoints scales the padding with the baseline, so data sitting high above zero in a narrow band gets a huge axis — ColCEN TE mCG spans 41.6–50.1 and was drawn on 33.3–60.1.
- `Profile__` and `Profile_pergroup__` are drawn in R (`workflow/scripts/R_profile.R` on `plot_profile.R`), not by `plotProfile`; `plotting_profile_on_targetfile` runs in `CONDA_ENV_PLOTS` and reads the matrix itself. `plot_profile.R` keeps the parts apart so the phase 3 heatmap's top profile reuses them: `profile_data` (the `group_means` curves, plus an se/std band), `profile_limits` (per-column y range of those very curves, via `plot_scales.R`'s `profile_ylims` — the y half of `matrix_scales`, without its percentile pass — for `type`/`sample`, `default_ylim` for `default`) and `profile_ggplot`. Curves and limits use the same `profiles_scale`, so no curve leaves its axis (deeptools drew `Profile__` as a mean even under median). Each panel spans exactly its limits: the se/std band and the fill (drawn down to the panel's ymin, not 0) are clipped to them, as deeptools clipped to `--yMin/--yMax` — otherwise a band would widen one panel of a mark and not another. The rule takes no `heat_m*` (they only set heatmap colours, and would rerun every profile). `Profile__`: a panel per matrix column in its display colour, each on its own column's limits (looked up by key, so interleaved stranded columns stay right; under `default`, each on its own curves' range), a line per region group told apart by dash. `Profile_pergroup__`: a panel per region group, a line per column, one shared range (`shared_ylim`); `heatmaps_scales: default` shares `default_scales`' range (the old awk collapse gave `--yMin 99999 --yMax -99999` and a blank plot). For mC and `all`, `Profile_pergroup__` is faceted on the key's mark instead (`plot_profile_by_context`; the context for mC): the columns are sample × mark and colours are keyed on `levels_label`, so one panel would draw a sample's mCG, mCHG and mCHH in one colour, and in `all` one shared range would flatten ChIP and mCHH against mCG. One row of panels (CG | CHG | CHH, each on the shared range of its context's columns, autoscaled under `default`), a line per series, a row per region group (`nostrand`). Series that share a colour are told apart by dash pattern. Labels, colours, tracks and series come from the display table (below). `profile_type` (theme) picks lines / fill / se / std. The heatmaps still come from deeptools.
- R plots take their look from `workflow/scripts/plot_theme.R`: built-in themes (`default`, `presentation`) as lists of keys (fonts, line widths, strips, legend sizing, fallback tab20 palette, heatmap colour ramps per data type, PDF panel sizes) plus helpers (`epicc_theme`, `epicc_ggtheme`, `epicc_gpar`, `epicc_dashes`, `epicc_legend_*`, `epicc_heatmap_colors`). The options YAML picks one with `plot_theme` and replaces keys with `plot_theme_overrides`. Unknown keys and type changes are errors raised in R; `heatmap_colors` is the one open map, and an entry there is a colour list or one matplotlib colour-map name (`viridis`, `RdBu_r`) looked up in `plot_colormaps.json` (regenerate with `dev/gen_plot_colormaps.py`). `plot_theme_spec` (`config_validation.py`) turns the choice into stable JSON (`PLOT_THEME_JSON`), which only plot rules take as a param, so a theme change reruns plots only. The rule writes it to `$TMPDIR/plot_theme.json` and passes the path as the script's last argument. Sample colours are not theme keys; they come from the display table. `R_DRAWN_PLOT_FAMILIES` (Snakefile; now `("profiles",)`) names the plot families drawn in R. `legacy_plot_params` translates `profiles_plot_params` onto theme keys (`--plotType X` or `--plotType=X` → `profile_type`) with a deprecation warning, printed only from the main process (`workflow.is_main_process`; every cluster job re-parses the Snakefile), and any other flag stops the run. The `heatmaps_plot_params` half of the translation comes back with the R heatmaps in phase 3, from branch `claude/r-plot-legacy-flags` (`fc1130c`). Moving the deeptools plots to R is planned in `dev/docs/r-plotting-plan.md`.
- The `all` env's matrix is never computed from the bigwigs: `joining_all_matrix` joins the `most` and mC final matrices (`workflow/scripts/matrix_join_all.py`), because computeMatrix takes one set of options per run and the non-mC ones (`--missingDataAsZero --skipZeros`) read an uncovered cytosine as 0 % methylation. Rows are joined per group on (chrom, start, end, name, strand) in the mC matrix's order, a region `--skipZeros` dropped from `most` gets 0 and one missing from mC gets NaN, and every column goes to one bin size, the gcd of `bs` and `bs_mc`, with bins repeated, because the R profiles draw every line on the first sample's bin axis. A `most`-only row goes after its predecessor in `most` (target-file order), rows with no data anywhere are dropped only when both inputs exist, and the script streams both files (about 100 MB at ColCEN TE scale). The phase 3 combined heatmap reads this matrix; don't join the two again elsewhere. A `ruleorder` puts it ahead of `merging_matrix`, whose output pattern also matches `all`.
- R plotting scripts read `computeMatrix` output through `workflow/scripts/matrix_io.R` (`read_matrix`, `group_means`, `sort_rows`, `bin_rows`, `matrix_ticks`), which reproduces deeptools: NaN-aware summaries, and `descend` as numpy's ascending argsort reversed (an all-NaN row goes to the top of its group). `tests/unit/test_matrix_io.py` compares it with `plotProfile`/`plotHeatmap` when deeptools is on PATH. `computing_matrix_scales` runs `workflow/scripts/R_matrix_scales.R` on `plot_scales.R`; it no longer calls deeptools (`dataRange`, `plotProfile`). It writes the same `--zMin/--zMax`, `--yMin/--yMax` files: one value per column in column order; `type`/`sample`/`default`; zMin/zMax are the 10th/90th percentiles `dataRange` gave, NaN-propagating, so mC always falls back to `heat_m*`; y comes from `group_means`, the averaging the R profiles draw with. R plots look scales up by column key with `scale_for_column`. One deliberate difference: the old awk searched a mark's range in `type` mode from the sentinels ±999999, so a mark whose 10th percentile was ≥ 999999 got zMin 0; R keeps the range, and the tests apply that one fix to the old output before comparing. The old bash + deeptools block is frozen in `dev/reference/computing_matrix_scales_deeptools.sh`, and `tests/unit/test_plot_scales.py` checks the rule gives the same doubles (live with `dev/scales_rule.py` when deeptools is on PATH). The rule runs in `workflow/envs/epibutton_plots.yaml` (`CONDA_ENV_PLOTS`), the env for R plotting and plot-scale rules. Keep new plotting packages there rather than in `epibutton.yaml`: a change to `epibutton.yaml` reruns every rule that shares it, genome prep and downloads included. The old rule's output for the test fixture is checked in (`tests/unit/data/plot_scales_golden.json`, from `dev/gen_plot_scales_golden.py`), so the comparison also runs without deeptools.
- Plot labels show a component only where it varies (`build_plot_labels` / `plot_label_parts` in `sample_sheet.py`, the one builder every combined-analysis call site uses: `define_key_for_plots`, `define_input_for_pca`, `define_samples_for_upset`). Call sites pass structured entries (`levels`, `mark`, `assay`, `replicate` — set only in all-replicates mode or for PCA points —, `sid`, `suffix`), never pre-joined strings. Over the samples plotted together, each Levels factor value, the mark, the assay (base token if that varies, full `_broad`/`_narrow` token if only the peak type varies) and the replicate are shown on every label if they vary and dropped if they don't; the assay is skipped on an entry whose mark already names it (`ATAC`, `RNAseq`/`RAMPAGE`, `sRNA_24nt`); a label left empty falls back to its full `levels_label`. Remaining ties get the full assay token, then the Sample_ID; `check_unique_labels` stays as the backstop. Colours stay keyed on the full `levels_label`. `omit=("mark",)` gives the mC per-context profile its line names (`"series"`), which `plot_profile_by_context` reads from the display table's fifth column instead of string-stripping `_<context>` — so it stays right when a CG-only `methylation_contexts` drops the context from the labels.
- Plot labels are cosmetic: no step that computes data takes a label or a colour, so a label change reruns only plotting jobs (Snakemake's params trigger would otherwise rebuild every matrix). Data steps name samples by stable keys — `computeMatrix --samplesLabel` and the browser's `multiBigwigSummary -l` / scratch tracks use `{sid}__{track}` (`define_key_for_plots(..., "keys")`, `sid` being the analysis name or replicate `mapped_name`), the PCA summaries use `mapped_name`, and the UpSet merge names samples by sample id. Plot rules join labels and colours back on: heatmap/profile rules pass a `key<TAB>label<TAB>colour<TAB>track<TAB>series` table (`"display"`) through `workflow/scripts/matrix_sample_labels.py`, which emits it in the matrix's own column order (so stranded and unstranded matrices both come out right); `make_single_loci_browser_plot` joins `"browser_display"` onto the extracted tracks; `plotPCA` gets `--labels`; the UpSet R scripts recode the merged file's Samples column from an `id=label` map (`"relabel"`, `recode_sample_ids` in `upset_common.R`, which resolves sRNA's `{id}_{sizeclass}` columns and stops on an id it can't map). `computing_matrix_scales` reads each column's mark back as the key's last `__` field, matched exactly (a substring `grep` let `H3K9me` claim `H3K9me2`), works out one range per mark and emits one value per column in column order — columns are not grouped by mark, since an unstranded matrix of a stranded track interleaves each sample's `_plus`/`_minus` columns, and the browser negates keys ending `_minus`. Don't reintroduce a label into a data rule's params; `tests/unit/test_cosmetic_plot_labels.py` checks.
- `--regionsLabel` is generated by `workflow/scripts/matrix_region_labels.py`, which reads the group structure out of the matrix header (`matrix_header.py`, shared with `matrix_sample_labels.py`). Don't derive it from the target file: the group count depends on whether a `nostrand` pass ran, and `--skipZeros` drops regions, so neither the number of labels nor the counts in them can be known from the BED.
- Zero-read samples fail at the earliest rule that can name the cause: the download rules reject an SRA run whose real layout contradicts `Read_layout` (and any empty FASTQ), `make_mc_bigwig_files` rejects a CX report with no covered cytosine, and `R_call_DMRs_pair_metilene.R` rejects a group with no usable position — metilene segfaults (exit 139) on that input rather than reporting an error.
- TMPDIR routing: `workflow/Snakefile` registers a `shell.prefix` that points TMPDIR at `{output_dir}/.tmp/${SLURM_JOB_ID:-local}.$$/` — keyed on both SLURM_JOB_ID (cross-node uniqueness under the SLURM executor) and `$$` (per-shell uniqueness), with a `trap rm` cleanup on EXIT. The `$$` is required: a local `--cores N` run launched inside a single sbatch allocation (no `--profile`) shares one SLURM_JOB_ID across all concurrent jobs, so keying on SLURM_JOB_ID alone would give them one shared scratch dir that the first job's EXIT trap deletes out from under its still-running siblings. Tools that spill through TMPDIR (sort, samtools, STAR, fasterq-dump, deeptools) write to the project filesystem instead of cluster `/tmp` — important on sites where `/tmp` is a RAM-tmpfs sized off `mem_mb` (e.g. SLURM `JobContainerType=job_container/tmpfs`). Opt out via `use_node_tmpdir: true` in the options file or `epicc run --use-node-tmpdir`. Bismark is the one mapper with its own `--temp_dir` pointed under `results/mC/mapped/<sample>/`, so it's unaffected by the TMPDIR override either way.
- dmC (ONT/PacBio) flow uses `modkit pileup` → bedMethyl → CX_report rather than DMRcaller's `readONTbam`. Reasons: (1) modkit is the de facto standard ONT methylation caller with calibrated probability filtering and broader mode support (5mC/5hmC/dual); (2) bedMethyl is a portable intermediate (IGV, methylpy, bsmooth can all consume it); (3) routing dmC through the same CX_report format as Bismark means the entire downstream pipeline (bigwigs, DMRs, PCA) has one code path; (4) `readONTbam`'s defaults are mammal-centric (`BSgenome.Hsapiens.UCSC.hg38`, CG-only, single 0.5 probability threshold) and would need plant BSgenome packages per genome and three separate calls per replicate for our 3-context use case.
- Bisulfite mapping uses the **Bismark 3.x Rust suite** (pinned `bismark>=3.1.0,<4` in `epibutton_mc.yaml`) — a single multi-call binary, but the classic tool names (`deduplicate_bismark`, `bismark_methylation_extractor`, `bismark2report`, `bam2nuc`) still work as aliases. The 3.x aligner recognises but does not yet implement `--nucleotide_coverage`, so `mC.smk` computes nucleotide-composition stats via a separate `bam2nuc` step on the deduplicated BAM (`{PE,SE}__<sample>.deduplicated.nucleotide_stats.txt`). The five bismark2report companion inputs (alignment/dedup/splitting/M-bias/nucleotide) are declared as tracked rule I/O so a missing one fails at mapping with a clear error rather than crashing report generation. See `dev/docs/upstream_blockers.md`.
- DMR pair-context jobs (`call_DMRs_for_pair_context`) run `computeDMRsReplicates` with `parallel=FALSE` and `cores=1L` — serial per-chromosome iteration. Parallel mode (`SnowParam(type="SOCK")` across chromosomes) consistently crashed BiocParallel's reducer on heterogeneous plant data with `Error: BiocParallel errors / wrong args for environment subassignment`, masking the underlying worker R error. A diagnostic with identical input + `parallel=FALSE` completes cleanly (verified PBAT__Col0_seedling vs WGBS__Col0_seedling CHG, 2026-05-18, 2147 DMRs in 56 min). Trade-off: high-coverage 4-replicate pairs (e.g. EMseq×EMseq on ColCEN-scale plant data) take 1–4 h serial vs ~10–20 min parallel-when-it-worked; bins method is still fast enough for this to be acceptable. The pooled fallback (`computeDMRs` for N<2 pairs) keeps parallel SnowParam since it doesn't trigger the bug.
- The shipped `profiles/slurm/config.yaml` sets `retries: 1` to absorb both transient SLURM control-plane glitches and the rare SnowParam port collisions that can still hit the pooled-fallback DMR path. Site profiles inheriting from it should keep `retries` at 1 or higher. It also sets `slurm-requeue: true`, which leaves node failures and preemption to SLURM's requeue and keeps the plugin tracking the job under its original ID. Without it, on a cluster with `JobRequeue=1` the plugin reports a `NODE_FAIL` as a failure and `retries` submits a second copy while SLURM's requeued one runs, and the two clobber each other's outputs (Bismark temp splits → bowtie2 "fewer reads in file specified with -1"). `slurm-no-requeue` is not the alternative: a preempted job is then cancelled and the plugin waits on it forever.
